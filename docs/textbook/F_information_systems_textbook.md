# 第1部：情報通信技術に関する基礎的知識（F-1〜F-11）

第1部は、コンピュータそのものの仕組み（ハードウェア・ソフトウェア）から、プログラムの作り方、システムの組み方、データベースやネットワークの基礎まで、「ITの土台となる知識」を扱います。普段スマートフォンやパソコンを何気なく使うときに裏側で動いている仕組みを、1つずつ言葉で説明できるようになることを目指しましょう。

## F-1：ハードウェア（構成要素、機能と処理）

### 基本概念

コンピュータは、大きく分けて5つの装置（**5大装置**）から成り立っています。スマートフォンで考えるとイメージしやすいです。

| 装置 | 役割 | スマホでの例 |
|---|---|---|
| **入力装置** | 外部からデータを取り込む | タッチパネル、マイク、カメラ |
| **記憶装置** | データやプログラムを保存する | 内蔵メモリ、SDカード |
| **演算装置** | 計算・処理を行う | CPU（の一部） |
| **制御装置** | 各装置に指示を出す | CPU（の一部） |
| **出力装置** | 処理結果を外部に表示・出力する | 画面、スピーカー |

このうち演算装置と制御装置をまとめて**CPU（中央処理装置）**と呼びます。CPUの性能は、1秒間に何回の処理ができるかを表す**クロック周波数**（単位：GHz）や、同時に処理できる作業単位である**コア数**（デュアルコア、クアッドコアなど）で表現されます。

記憶装置には2種類あります。

- **主記憶装置（メモリ、RAM）**：CPUが直接読み書きする作業用の記憶装置。電源を切るとデータが消える（**揮発性**）。パソコンで多くのアプリを同時に開くと重くなるのは、RAMの容量が足りなくなるためです。
- **補助記憶装置**：電源を切ってもデータが消えない（**不揮発性**）長期保存用の記憶装置。HDD（ハードディスク、磁気で記録）とSSD（半導体メモリで記録、HDDより高速・高価）があります。スマホの「内蔵ストレージ」はこちらに当たります。

なお、**ROM（Read Only Memory）**は主に読み出し専用の記憶素子で、こちらも電源を切ってもデータが消えない不揮発性メモリです（BIOSの起動プログラムなどが格納されます）。「RAM＝揮発性」「ROM・HDD・SSD＝不揮発性」という対比を押さえておきましょう。

補助記憶装置の信頼性を高める技術が**RAID（レイド）**です。複数台のディスクを組み合わせて、速度向上や故障対策を行います。

| RAIDレベル | 仕組み | 特徴 |
|---|---|---|
| **RAID0** | データを複数台に分散して書き込む（ストライピング） | 高速化できるが、1台故障すると全データが失われる（冗長性なし） |
| **RAID1** | 同じデータを2台に同時に書き込む（ミラーリング） | 1台故障しても継続稼働できるが、実質容量は半分になる |
| **RAID5** | データとパリティ（誤り訂正用の符号）を複数台に分散 | 最低3台必要。1台までの故障に耐えられる |
| **RAID6** | RAID5に加えパリティを二重化 | 最低4台必要。2台までの故障に耐えられる |

### 具体例

ノートパソコンで動画編集ソフトを使うと動作が重くなるのは、動画データを一時的にRAM（主記憶）に大量に読み込むためです。RAMを増設すると、同時に多くの作業を快適にこなせるようになります。一方、パソコンの電源を切っても書きかけの文書ファイルが消えないのは、そのファイルがSSD（補助記憶装置）という不揮発性の場所に保存されているためです。

### ひっかけポイント

「主記憶装置は不揮発性で、電源を切ってもデータが保持される」という記述は誤りです（主記憶＝RAMは揮発性）。また、RAIDのレベルごとの最低必要台数・耐えられる故障台数（RAID1は1台、RAID5は1台、RAID6は2台まで）を数値で入れ替えるひっかけ問題が頻出なので、表で正確に覚えておきましょう。

## F-2：ソフトウェア（OS、ミドルウェア、パッケージ）

### 基本概念

ソフトウェアは、コンピュータに「何をするか」を指示するプログラム群です。役割によって階層があります。

1. **OS（オペレーティングシステム、基本ソフトウェア）**：ハードウェアを直接管理し、複数のアプリが動くための土台を提供する（例：Windows、macOS、Android、iOS、Linux）。ハードウェア資源の管理（メモリ管理、ファイル管理）、複数の処理を切り替えて動かす管理（ジョブ管理・タスク管理）を担う。
2. **ミドルウェア**：OSとアプリケーションソフトの中間に位置し、特定の機能をアプリに提供する（例：データベース管理システム＝DBMS、Webサーバソフト）。多くのアプリが共通して使う機能を、個々のアプリで作り込まずに済むようにする役割。
3. **アプリケーションソフト（応用ソフトウェア）**：利用者が実際に使う目的別のソフト（例：ワープロソフト、会計ソフト、SNSアプリ）。既製品として販売される**パッケージソフトウェア**と、自社専用に作られる**オーダーメイド（個別開発）ソフトウェア**がある。

### 具体例

スマホで家計簿アプリ（アプリケーションソフト）を使うとき、そのアプリはAndroidやiOSという土台（OS）の上で動いており、データの保存にはOSが提供するファイル管理の仕組みを利用しています。企業のWebサイトでは、Webサーバソフト（ミドルウェア）が、利用者からのアクセス要求を受け付け、必要に応じてデータベース（別のミドルウェア）からデータを取り出してアプリケーションに渡す、という役割分担をしています。

### ひっかけポイント

「ミドルウェアはOSの一部である」という記述は誤りです。ミドルウェアはOSとは独立してインストールされる、OSとアプリの中間層のソフトウェアです。また、パッケージソフトウェアは自社の業務に合わせて自由にゼロから設計できるわけではなく、あくまで既製の機能の範囲内でカスタマイズする点も、オーダーメイド開発との違いとして問われやすいポイントです。

## F-3：プログラム設計（アルゴリズム、データ構造）

### 基本概念

**アルゴリズム**とは、問題を解決するための「手順」のことです。料理のレシピのように、「何を、どの順番で行うか」を明確にしたものだと考えてください。アルゴリズムは**フローチャート**（流れ図）という図で表現されることがよくあります。

代表的なアルゴリズムには次のようなものがあります。

- **探索アルゴリズム**：データの中から目的のものを見つける方法。先頭から順番に1つずつ調べる**線形探索**と、データが並び替えられている前提で中央の値と比較しながら範囲を半分ずつ絞り込む**二分探索**（後者の方が高速）
- **整列（ソート）アルゴリズム**：データを大小順に並べ替える方法。隣り合う要素を比較して入れ替えていく**バブルソート**、基準値（ピボット）より大小で分割していく**クイックソート**（一般に高速）など

アルゴリズムの効率の良さは、データ量が増えたときに処理時間がどれくらい増えるかで評価します。これを**計算量（オーダー、O記法）**と呼びます。O(1)（データ量に関係なく一定）＜O(log n)（対数的に緩やかに増加、二分探索が該当）＜O(n)（データ量に比例、線形探索が該当）＜O(n²)（データ量の2乗で急増、単純な整列アルゴリズムが該当）の順に、一般に効率が良い（速い）とされます。

また、プログラムでデータを扱う際の「データの入れ物の形」を**データ構造**と呼びます。

| データ構造 | 特徴 | 身近な例 |
|---|---|---|
| **配列** | 同じ種類のデータを連続した場所に並べて格納。番号（添字）で直接アクセスできる | 座席番号で管理された座席表 |
| **リスト（連結リスト）** | データ同士を「次はこれ」という矢印（ポインタ）でつなげる。途中への挿入・削除が得意 | 電車の連結車両 |
| **スタック** | 後から入れたものを先に取り出す（**LIFO**：Last In First Out） | 積み重ねたお皿（上から取る） |
| **キュー** | 先に入れたものを先に取り出す（**FIFO**：First In First Out） | レジの待ち行列（先着順） |
| **木構造** | 親子関係で階層的にデータをつなげる | 会社の組織図、パソコンのフォルダ構造 |

### 具体例

スマホの連絡先アプリで、五十音順に並んだ連絡先の中から特定の相手を探すとき、上から1件ずつ確認する（線形探索）よりも、あらかじめ並んでいることを利用して真ん中から絞り込む（二分探索）方が速く見つかります。また、「元に戻す（Undo）」機能は、直前の操作を後入れ先出し（スタック）の形で記録しているため実現できます。

### ひっかけポイント

スタック（LIFO：後入れ先出し）とキュー（FIFO：先入れ先出し）の入出力順序を逆に覚えてしまうミスが非常に多いので注意してください。また「二分探索はデータが並び替えられていなくても使える」という記述は誤りです。二分探索は、データが事前にソート（整列）されていることが前提の手法です。計算量の大小関係（O(log n) < O(n) < O(n²)）を逆に覚える誤りにも注意しましょう。

## F-4：ソフトウェア開発（構造化、オブジェクト指向）

### 基本概念

プログラムを「わかりやすく、直しやすく」作るための考え方（プログラミングパラダイム）として、代表的なものが2つあります。

**構造化プログラミング**は、どんなに複雑な処理も、次の3つの基本構造の組み合わせだけで表現できるという考え方です。

1. **順次構造**：上から下へ、書かれた順番に処理を実行する
2. **選択（分岐）構造**：条件によって処理を分ける（もし〇〇なら△△する、そうでなければ□□する）
3. **反復（繰り返し）構造**：条件を満たす間、同じ処理を繰り返す

さらに、大きなプログラムを機能ごとの部品（モジュール）に分割して設計する**モジュール分割**（トップダウンで全体から部分へ設計を進める）も構造化プログラミングの重要な考え方です。

**オブジェクト指向**は、データとそれを操作する処理を「モノ（オブジェクト）」としてひとまとめにして設計する考え方です。3つの重要な性質があります。

- **カプセル化**：データとそれを操作する処理を1つの部品（クラス）の中にまとめ、外部からは決められた方法（インタフェース）でしかアクセスできないようにすること。内部の実装を隠すことで、他の部分への影響を抑える
- **継承**：既存のクラス（親クラス）が持つ性質を、新しいクラス（子クラス）が引き継ぐこと。共通部分を再利用でき、開発効率が上がる
- **ポリモーフィズム（多相性）**：同じ名前の命令（メソッド）を呼び出しても、オブジェクトの種類によって実際の処理内容が異なる性質

なお、クラスから実際に作られた実体を**インスタンス**と呼びます。クラスは「設計図」、インスタンスは設計図から作られた「実物」だとイメージすると理解しやすいです。

### 具体例

家計簿アプリを構造化プログラミングで作る場合、「入力を受け取る」「合計を計算する」「表示する」といった処理を順番に実行しつつ（順次）、「支出か収入かによって処理を分ける」（選択）、「入力された件数分だけ繰り返し集計する」（反復）という組み合わせで作られています。オブジェクト指向で考えるなら、「車」というクラス（設計図）に「走る」「止まる」という共通の操作（メソッド）を定義しておき、「スポーツカー」クラスがそれを継承しつつ独自の「加速する」処理を追加する、というイメージです。

### ひっかけポイント

「カプセル化とは、複数のクラスをまとめて1つの大きなクラスにすることである」という説明は誤りです。カプセル化は、データと処理を1つのオブジェクトにまとめ、内部の詳細を外部から隠すことを指します。また「継承とは、あるクラスの機能を別のクラスが呼び出して使うことである」という説明も不正確で、継承は親クラスの性質を子クラスが引き継ぐ関係を指し、単なる呼び出し（利用）とは異なる概念です。

## F-5：システム構成（クライアントサーバ、仮想化）

### 基本概念

複数のコンピュータをどう組み合わせてシステムを作るか、という話です。

**クライアントサーバシステム**は、サービスを提供する側（**サーバ**）と、サービスを利用する側（**クライアント**）に役割を分けた仕組みです。例えば、社内の共有ファイルを保管する「ファイルサーバ」に、各社員のパソコン（クライアント）がアクセスする形です。処理の分担の仕方によって、クライアント側に処理を多く持たせる**2層クライアントサーバ**と、クライアント・アプリケーションサーバ・データベースサーバのように役割をさらに分ける**3層クライアントサーバ**があります。

これとは異なる方式として、サーバを介さず、対等な立場のコンピュータ同士が直接データをやり取りする**ピアツーピア（P2P）方式**もあります（ファイル共有ソフトなどで使われる）。

**仮想化技術**は、1台の物理的なコンピュータ（ハードウェア）の上に、複数の独立した仮想的なコンピュータ環境を作り出す技術です。仮想化を実現するソフトウェアを**ハイパーバイザー**と呼びます。1台の高性能なサーバを仮想化して複数の仮想サーバとして使うことで、ハードウェアの導入コストを抑えつつ柔軟にシステムを増減できます。近年は、仮想化よりも軽量にアプリの実行環境を分離する**コンテナ技術**（代表例：Docker）も普及しています。

システムを止めないための工夫として、同じ処理を行う2つの系統を同時に稼働させる**デュアルシステム**（片方が故障してももう片方が処理を続ける、信頼性重視）や、普段は主系統だけで処理を行い、故障時に予備系統に切り替える**デュプレックスシステム**（コストを抑えつつ信頼性を確保）もこの分野の重要な用語です。

### 具体例

ネットショップでは、利用者が操作するスマホ・パソコン（クライアント）からの注文を、Webサーバが受け付け、その裏でアプリケーションサーバが在庫確認などの処理を行い、データベースサーバが商品情報や注文履歴を管理する、という3層クライアントサーバの構成が一般的です。また、1台の物理サーバの上に「Webサーバ用の仮想マシン」と「メール用の仮想マシン」を同時に動かすのは仮想化の典型的な活用例です。

### ひっかけポイント

「P2P方式は、クライアントサーバ方式の一種であり、サーバの機能を複数のコンピュータで分担する仕組みである」という説明は誤りです。P2Pはサーバを介さず対等なコンピュータ同士が直接通信する方式であり、クライアントサーバ方式とは異なる概念です。また、仮想化技術は「1台のコンピュータで複数のアプリを同時に起動できるようにする技術（マルチタスク）」とは異なり、独立したOS環境（仮想マシン）そのものを複数動かせる点が特徴です。

## F-6：情報処理の形態（集中/分散/並列、リアルタイム/バッチ）

### 基本概念

コンピュータでの処理のやり方には、いくつかの分類軸があります。

**処理場所による分類**：
- **集中処理**：1台の大型コンピュータ（ホストコンピュータ）に処理を集約する方式。管理はしやすいが、そのコンピュータが故障すると全体が止まる
- **分散処理**：複数のコンピュータに処理を分散させる方式。柔軟性・拡張性は高いが、管理は複雑になる

**処理単位による分類**：
- **並列処理**：複数のCPU（コア）で処理を同時並行して実行し、全体の処理時間を短縮する方式

**処理タイミングによる分類**：
- **リアルタイム処理**：データが発生した都度、即座に処理して結果を返す方式（例：ATMでの入出金処理、鉄道の座席予約システム）
- **バッチ処理**：一定量、または一定期間のデータをためておき、まとめて一括処理する方式（例：夜間にまとめて実行される給与計算、月次の請求書発行）

### 具体例

ATMで現金を引き出すと、その場で口座残高が減り、即座に結果（明細書や残高）が返ってきます。これは1件ごとに即時処理するリアルタイム処理の例です。一方、企業の給与計算システムでは、月末に全社員分の勤怠データをまとめて処理し、翌朝までに給与明細を一括作成します。これは、即時性よりも大量データの効率的な処理を優先するバッチ処理の例です。

### ひっかけポイント

「バッチ処理は処理結果がすぐに得られるため、緊急性の高い業務に向いている」という記述は誤りです。バッチ処理はデータをためて一括処理する方式のため、処理結果が得られるまでに時間がかかります。緊急性・即時性が求められる業務にはリアルタイム処理が適しています。用途（ATM＝リアルタイム、給与計算＝バッチ）とセットで覚えておくと混同しにくくなります。

## F-7：ヒューマンインタフェース（Webデザイン、マルチメディア）

### 基本概念

**ヒューマンインタフェース**とは、人間とコンピュータとの間で情報をやり取りする接点（画面や操作方法）のことです。文字だけで操作するCUI（キャラクタユーザインタフェース）に対し、アイコンやウィンドウを指やマウスで直感的に操作できる**GUI（グラフィカルユーザインタフェース）**が現在は主流です。

Webサイトやアプリのデザインを評価する際の重要な観点が2つあります。

- **ユーザビリティ**：目的の操作を、どれだけ効率よく・迷わず・快適に行えるか（使いやすさ）
- **アクセシビリティ**：年齢・障がいの有無・利用環境などにかかわらず、誰もが情報や機能に到達し利用できるか（利用しやすさの公平性。例：色覚特性に配慮した配色、画面の内容を音声で読み上げる機能への対応）

**マルチメディア**とは、文字・音声・静止画・動画などの複数のメディア（表現形式）を組み合わせて扱う技術です。動画や音声、画像はデータ量が大きいため、データを小さくする**圧縮**技術が使われます。

- **可逆圧縮**：圧縮したデータを完全に元通りに復元できる方式（例：ZIP、PNG、FLAC）。データの欠落は許されない文書や一部の画像形式に使われる
- **非可逆圧縮**：一部の情報を間引いて捨てることで、より高い圧縮率を実現する方式（例：JPEG、MP3、MPEG）。人間の目や耳では気づきにくい情報を削るため、動画・音声・写真など多少の劣化が許容される用途で広く使われる

### 具体例

スマホで写真を撮ると、そのファイルは多くの場合JPEG形式（非可逆圧縮）で保存されます。多少画質が劣化しても、ファイルサイズを大きく小さくできるためです。一方、業務システムの帳票データをそのまま正確に保存したい場合は、可逆圧縮であるZIP形式などが選ばれます。また、視覚に障がいのある利用者のために、Webサイトの画像に代替テキスト（読み上げ用の説明文）を設定するのは、アクセシビリティ向上の取り組みの一例です。

### ひっかけポイント

「JPEGは可逆圧縮形式であり、圧縮後も元の画質を完全に復元できる」という記述は誤りです。JPEGは非可逆圧縮の代表例で、圧縮すると元の画質には戻せません。また、「ユーザビリティが高ければアクセシビリティも自動的に満たされる」という考え方も誤りです。両者は似ていますが別の観点（使いやすさ vs 利用できる対象の広さ）であり、意図的に両方を設計に組み込む必要があります。

## F-8：外部情報資源の活用（クラウド、OSS）

### 基本概念

自社で全てのシステムを保有・運用するのではなく、社外の情報資源を活用する動きが広がっています。代表格が**クラウドコンピューティング**です。インターネット経由で、サーバやソフトウェアなどの情報資源を必要な分だけ利用できるサービス形態で、自社でハードウェアを購入・管理する必要がないのが特徴です。クラウドサービスは、どこまでを事業者が提供し、どこからを利用者が管理するかによって3つに分類されます。

| 分類 | 提供される範囲 | 利用者が用意・管理する部分 | 例 |
|---|---|---|---|
| **SaaS**（Software as a Service） | アプリケーションソフトそのもの | データの入力・利用のみ | Gmail、会計クラウドサービス |
| **PaaS**（Platform as a Service） | アプリケーションを開発・実行するための基盤（OS、DB等） | 自社で開発したアプリケーション | 開発プラットフォームサービス |
| **IaaS**（Infrastructure as a Service） | サーバ・ストレージ・ネットワークなどのインフラのみ | OS、ミドルウェア、アプリケーション全て | 仮想サーバ貸し出しサービス |

もう1つの重要な外部情報資源が**OSS（オープンソースソフトウェア）**です。ソースコード（プログラムの設計図に当たる文書）が公開されており、一定のライセンス条件の下で誰でも自由に利用・改変・再配布できるソフトウェアです。無償で高機能なソフトウェアを利用できる一方、利用にあたってはライセンス（利用許諾条件。改変後の公開義務の有無など、ライセンスの種類によって条件が異なる）の内容を確認する必要があります。

### 具体例

中小企業が自社でメールサーバを構築・運用する代わりに、クラウド型のメールサービス（SaaS）を月額料金で利用すれば、サーバの保守・セキュリティ対応の手間を大幅に減らせます。自社独自の業務アプリを開発したい場合は、開発環境が整ったPaaSを使えば、OSやミドルウェアの構築の手間を省いて開発に集中できます。また、Webサーバの構築によく使われるソフトウェアの多くはOSSとして無償で公開されています。

### ひっかけポイント

SaaS・PaaS・IaaSは「利用者がどこからどこまで自分で用意・管理する必要があるか」の範囲で区別します。「SaaSは、利用者が自らアプリケーションを開発してサーバ上で稼働させるサービス形態である」という説明は誤りです（それはPaaSの説明）。また「OSSは無償だが改変や再配布は一切禁止されている」という記述も誤りです。多くのOSSはライセンスの条件を守れば改変・再配布が可能であり、それこそがOSSの特徴です（ただしライセンスの種類によって条件は異なります）。

## F-9：データベースの種類と構成、DBMS（正規化）

### 基本概念

**データベース**とは、大量のデータを整理して保存し、後から検索・更新しやすくした仕組みです。最も広く使われているのが、データを「表（テーブル）」の形で管理する**リレーショナルデータベース（RDB）**です。表の各行を一意に識別するための項目を**主キー**、他の表の主キーを参照するための項目を**外部キー**と呼び、これによって複数の表同士を関連づけます。

データベースを管理するソフトウェアを**DBMS（データベース管理システム）**と呼びます。DBMSは主に次の機能を持ちます。

- **排他制御**：複数の利用者が同時に同じデータを更新しようとしたときに、データの矛盾が生じないよう制御する機能
- **トランザクション管理**：一連の処理（例：口座Aから引き落として口座Bに入金する）を「すべて成功」か「すべて失敗（取り消し）」のどちらかにまとめて扱う機能。この一連の処理の単位を**トランザクション**と呼び、トランザクションが満たすべき4つの性質を**ACID特性**と呼ぶ（原子性：全部成功か全部失敗かのどちらか、一貫性：処理前後でデータの整合性が保たれる、独立性：複数のトランザクションが互いに干渉しない、永続性：完了した処理結果は障害が起きても失われない）
- **バックアップ・リカバリ**：データを定期的に複製しておき、障害発生時に復旧できるようにする機能

表の設計を整理し、データの重複や更新時の矛盾を防ぐ手法が**正規化**です。正規化には段階があり、後の段階に進むほど、より厳密にデータの重複・矛盾のリスクを排除します。

| 正規形 | 満たすべき条件 |
|---|---|
| **第1正規形（1NF）** | 各セル（項目）に単一の値のみが入っており、繰り返し項目（同じ属性の値が1行に複数入る構造）がない |
| **第2正規形（2NF）** | 第1正規形であり、かつ非キー属性が主キーの一部にのみ依存する状態（部分関数従属）が存在しない（主キーが単一属性の表は、第1正規形であれば自動的に第2正規形も満たす） |
| **第3正規形（3NF）** | 第2正規形であり、かつ非キー属性同士が、別の非キー属性を経由して間接的に決まる関係（推移的関数従属）が存在しない |

### 具体例

ある学校の講座管理表に「開講コード（主キー）」「講座コード」「講座名」「講師コード」「講師名」の列があり、複数の開講コードで同じ講座コード・講座名の組み合わせが繰り返し登場するとします。この場合、「開講コード→講座コード→講座名」というように、講座コードを経由して間接的に講座名が決まる関係（推移的関数従属）が生じています。これは第3正規形の条件に違反しているため、「開講講座マスタ（講座コード・講座名）」という別の表に分割することで、講座名の重複入力・更新漏れを防ぐことができます。

### ひっかけポイント

主キーが単一の属性（複合キーではない）の表は、第1正規形を満たしていれば自動的に第2正規形の条件もクリアします（部分関数従属は、複合キーの場合にのみ発生しうる問題だからです）。したがって「主キーが1つの属性しかない表なのに、第2正規形を満たさない」という記述は誤りである可能性が高い点に注意しましょう。また、ACID特性の4つの用語（原子性・一貫性・独立性・永続性）の定義を入れ替えるひっかけにも注意が必要です。

## F-10：通信ネットワークの種類と構成、プロトコル

### 基本概念

複数のコンピュータをつなぐ仕組みがネットワークです。会社や自宅など限られた範囲内のネットワークを**LAN（Local Area Network）**、地理的に離れた拠点同士をつなぐ広域のネットワークを**WAN（Wide Area Network）**と呼びます。

コンピュータ同士が通信するための「共通のルール」を**プロトコル**と呼びます。プロトコルは役割ごとに階層化されており、代表的な整理の仕方が**OSI参照モデル**（7階層）です。

| 層（上位→下位） | 役割 | 代表的なプロトコル・技術 |
|---|---|---|
| 7 アプリケーション層 | 具体的な通信サービスの提供 | HTTP、SMTP、FTP |
| 6 プレゼンテーション層 | データの形式（文字コード、圧縮、暗号化）の変換 | |
| 5 セッション層 | 通信の開始・終了の管理 | |
| 4 トランスポート層 | 通信の信頼性・速度の制御 | TCP、UDP |
| 3 ネットワーク層 | 宛先までの経路選択・アドレス指定 | IP |
| 2 データリンク層 | 直接つながった機器間のデータ転送 | イーサネット |
| 1 物理層 | 電気信号・光信号など物理的な伝送 | ケーブル、無線 |

実務でよく使われる主要プロトコルの役割は次の通りです。

- **TCP**：接続を確立し、データの到達確認・再送制御を行う信頼性重視のプロトコル
- **UDP**：接続確立や再送制御を行わず、速度・リアルタイム性を重視するプロトコル（動画配信等で利用）
- **IP**：宛先IPアドレスに基づく経路選択（ルーティング）とアドレス指定を担うプロトコル
- **DHCP**：ネットワークに接続した機器にIPアドレス等の設定情報を自動的に割り当てるプロトコル
- **ARP**：IPアドレスから同一ネットワーク内の機器のMACアドレス（機器固有の識別番号）を解決するプロトコル
- **DNS**：人間が覚えやすいドメイン名（例：example.com）を、通信に必要なIPアドレスに変換する仕組み
- **HTTP／HTTPS**：Webページのデータをやり取りするためのプロトコル（HTTPSは通信内容を暗号化した安全な版）
- **SMTP**：電子メールを送信するためのプロトコル

### 具体例

スマホでWebブラウザにサイトのアドレス（ドメイン名）を入力すると、まずDNSがそのドメイン名に対応するIPアドレスを調べ、そのIPアドレスに向けてHTTPS（暗号化された通信）でページのデータを要求します。自宅のWi-Fiルーターに新しいスマホを接続すると、DHCPが自動的にそのスマホにIPアドレスを割り当ててくれるため、利用者が手動で設定しなくてもインターネットにつながります。

### ひっかけポイント

「信頼性よりも速度を重視し再送制御を行わないプロトコル」はUDP（TCPではない）、「IPアドレス等の設定情報を自動的に割り当てるプロトコル」はDHCP（機器の稼働状況監視を行うSNMPではない）、「経路選択とアドレス指定を行うプロトコル」はIP（同一セグメント内のアドレス解決のみを行うARPではない）というように、似た用語の役割を入れ替えるひっかけが頻出です。「信頼性のTCP・速度のUDP」「自動割当のDHCP」「経路選択のIP」「アドレス解決のARP」「監視のSNMP」という役割をセットで覚えておきましょう。

## F-11：システム評価（性能、信頼性、経済性）

### 基本概念

情報システムの良し悪しは、複数の観点から評価されます。

**性能評価の指標**：
- **スループット**：単位時間あたりに処理できる量（処理能力）
- **レスポンスタイム**：処理を依頼してから最初の反応が返ってくるまでの時間
- **ターンアラウンドタイム**：処理を依頼してから、すべての結果が返ってくるまでの時間

**信頼性を高める設計の考え方**は、故障や誤操作への対応方針によっていくつもの専門用語があります。

| 用語 | 考え方 |
|---|---|
| **フォールトアボイダンス** | 部品一つひとつの品質・信頼性を高め、そもそも故障が発生しないようにする |
| **フォールトトレランス** | 部品を多重化・冗長化し、一部が故障しても全体としては正常に稼働し続けられるようにする |
| **フェイルセーフ** | 故障が発生した際に、システムを安全側の状態に導き、被害を最小限に抑える |
| **フェイルソフト（フォールバック）** | 故障が発生した際に、一部機能を制限（縮退）してでも、重要な機能だけは稼働し続けさせる |
| **フェイルオーバ** | 稼働系に障害が起きた際、処理を待機系（バックアップ系統）に自動的に切り替える |
| **フールプルーフ** | 利用者の誤操作があっても、危険な状態が生じないように設計する |

信頼性を数値で表す代表的な指標に、**MTBF（平均故障間隔）**（故障から次の故障までの平均時間、長いほど信頼性が高い）と**MTTR（平均修復時間）**（故障してから復旧するまでの平均時間、短いほど良い）があります。システムが正常に稼働している割合を示す**稼働率（可用性）**は次の式で求められます。

$$稼働率 = \frac{MTBF}{MTBF + MTTR}$$

**経済性の評価**では、導入時の費用だけでなく、運用・保守・廃棄までの全期間にかかる総費用である**TCO（総所有コスト）**という考え方が重要です。安価に導入できても、保守費用が高額なシステムはTCOで見ると割高になることがあります。

### 具体例

ある工場の生産管理システムで、MTBFが200時間、MTTRが10時間だとすると、稼働率は200÷(200+10)≒0.952、つまり約95.2％と計算できます。この数値を高めるには、故障間隔を延ばす（MTBFを大きくする、フォールトアボイダンスの発想）か、復旧時間を短くする（MTTRを小さくする）工夫が必要です。

### ひっかけポイント

「フェイルオーバ」（待機系への切り替え）と「フェイルソフト・フォールバック」（機能を縮退させて稼働継続）、「フォールトアボイダンス」（故障を未然に防ぐ）と「フォールトトレランス」（故障しても全体は動き続ける）は、名前が似ているため入れ替えて出題されやすい組み合わせです。「事前に防ぐ（アボイダンス）」「起きても耐える（トレランス）」「起きたら安全側（セーフ）」「起きたら縮退（ソフト）」「起きたら切り替え（オーバ）」というように、故障発生の前か後か、どう対応するかで整理すると混同しにくくなります。

### 過去問で確認する
`problem_sets/1st_stage/exercises/F_information_systems_exercises.md` の「F-11：システム評価（性能、信頼性、経済性）」を参照。

# 第2部：経営情報管理（F-12〜F-24）

第2部は、ITそのものの技術知識ではなく、「経営にITをどう活かすか」「ITシステムをどう作り、どう守り、どう評価するか」というマネジメントの視点を扱います。中小企業診断士としては、この分野の知識をもとに、経営者に対してIT投資やシステム開発の助言を行うことになります。

## F-12：情報システム戦略（経営戦略との連携、システム化計画）

### 基本概念

**情報システム戦略**とは、会社の経営戦略（何を目指すか）を実現するために、情報システムをどう位置づけ、どう整備していくかという方針のことです。単に「便利そうだから」という理由でシステムを導入するのではなく、経営戦略と一貫性を持たせることが重要です。

情報システムを実際に整備する際は、一般に次のような段階を踏みます。

1. **全体最適化計画**：会社全体として、どの業務にどのようなシステムを配置すべきかという大きな設計図を描く
2. **個別システム化構想・計画**：全体最適化計画をもとに、個別のシステムをいつ、どのように開発するかを具体化する
3. **開発・導入**
4. **運用・保守・評価**

こうした情報システム戦略全体を統括する経営層の役職を**CIO（最高情報責任者）**と呼びます。CIOは、IT部門の代表であると同時に、経営戦略とIT戦略を橋渡しする役割を担います。

### 具体例

ある製造業の会社が「多品種少量生産への対応力強化」という経営戦略を掲げたとします。この戦略を実現するために、生産管理システムを刷新して製造ラインの切り替え時間を可視化・短縮する、という情報システム戦略を立てるのは、経営戦略とIT戦略が連携している例です。逆に、経営戦略と無関係に「流行っているから」という理由だけで高額なシステムを導入すると、投資対効果が見合わないリスクが高まります。

### ひっかけポイント

情報システム戦略は「個別のシステムをどう開発するか」という現場レベルの話（F-16・F-17の情報システム開発の話）とは異なり、より上位の「経営戦略とどう整合させるか」という話である点を区別しましょう。全体最適化計画（会社全体の設計図）を経ずに、いきなり個別のシステム化計画から着手すると、部門ごとにバラバラなシステムが乱立する「サイロ化」を招きやすい、という文脈もよく問われます。

## F-13：経営革新と情報システム（DX、業務プロセス改善）

### 基本概念

**DX（デジタルトランスフォーメーション）**とは、単にITツールを導入して業務を効率化する（デジタル化）にとどまらず、デジタル技術の活用を通じて、業務プロセス・組織・企業文化・ビジネスモデルそのものを変革し、競争優位を確立することを指します。経済産業省の「DX推進ガイドライン」等でも、この「変革」の側面が強調されています。

業務プロセスを抜本的に見直し、再設計する取り組みを**BPR（ビジネスプロセスリエンジニアリング）**と呼びます。既存の業務のやり方を前提とせず、ゼロベースで「本来どうあるべきか」を考え直す点が特徴です。

近年注目されている技術に、パソコン上の定型的な事務作業（データ入力、転記、集計など）をソフトウェアのロボットに自動で行わせる**RPA（ロボティック・プロセス・オートメーション）**があります。人手不足が課題の中小企業でも、比較的低コストで導入しやすい業務効率化の手段として普及が進んでいます。

また、古くから使われ続けている、更新や連携が難しくなったシステムを**レガシーシステム**と呼びます。経済産業省の報告書では、レガシーシステムを放置すると2025年以降、多額の経済損失が生じる可能性があるという「**2025年の崖**」という問題提起がなされ、DX推進の必要性を訴える文脈でよく引用されます。

### 具体例

紙の伝票をExcelに手入力していた業務を、そのままシステム化して「入力する画面」をパソコンに変えただけでは単なるデジタル化（IT化）にとどまります。一方、伝票そのものを電子化し、取引先とのデータ連携・自動集計・分析まで一体化させ、これまで人手に頼っていた発注判断をデータに基づいて行えるようにビジネスの進め方自体を変えるのであれば、それはDXと呼べる取り組みです。RPAを使えば、毎月の請求書データをシステムから抽出し会計ソフトに転記する定型作業を、ロボットに自動で行わせることができます。

### ひっかけポイント

「DXとは、単に紙の書類をデータ化すること（デジタイゼーション）を指す」という説明は不十分です。DXは、デジタル化（デジタイゼーション）やデジタル化された個々の業務プロセスの効率化（デジタライゼーション）を土台にしつつ、それらを通じてビジネスモデルや組織のあり方まで変革することを指す、より広い概念である点を区別しましょう。

## F-14：ITガバナンス（内部統制、システム監査）

### 基本概念

**ITガバナンス**とは、経営者が主体となって、情報システムへの投資や運用が経営戦略に沿って適切に行われているかを統制する仕組みです。関連する重要な2つの概念があります。

- **内部統制**：会社が経営目標を達成し、不正やミスを防ぐために自ら構築・運用する社内のルール・仕組み。経営者自身の責任で整備される。統制環境（会社全体の意識・体制）、リスクの評価と対応、統制活動（承認・チェックの仕組み）、情報と伝達、モニタリング（監視・改善）といった要素で構成される（COSOフレームワークの考え方）
- **システム監査**：情報システムが適切に管理・運用されているかを、開発や運用を行う部門から**独立した第三者（監査人）**の立場でチェックし、問題点を指摘・助言する活動。内部統制が経営者自身による「自己点検・運用の仕組み」であるのに対し、システム監査は独立した立場からの「客観的な検証」である点が異なる

### 具体例

社内で、システムの利用権限を「申請→上長の承認→システム管理者が付与」という手順にしているのは内部統制（統制活動）の一例です。この統制の仕組みが実際に機能しているかどうかを、開発・運用を行った部門とは別の立場の監査人が定期的にチェックし、「権限の見直しが長期間行われていない利用者がいる」といった問題点を指摘するのが、システム監査の役割です。

### ひっかけポイント

内部統制とシステム監査を混同しないようにしましょう。内部統制は「経営者自身が構築・運用する社内の仕組み」であるのに対し、システム監査は「独立した第三者の立場から、その仕組みが適切に機能しているかを検証・評価する活動」です。「システム監査は、開発を担当したシステム部門が自ら行う」という記述は、独立性の観点から誤りです。

## F-15：情報システムの適用領域（SCM、CRM）

### 基本概念

経営のさまざまな場面で活用される代表的な情報システムを整理します。

- **ERP（統合基幹業務システム）**：会計、人事、生産、販売など、会社の基幹業務（コアとなる業務）のデータを一元的に管理・連携させるシステム。部門ごとにバラバラだったデータを統合することで、経営状況をリアルタイムに把握しやすくする
- **SCM（サプライチェーンマネジメント）**：原材料の調達から、生産、物流、販売に至る一連の供給の流れ（サプライチェーン）を、企業の垣根を越えて一気通貫で最適化するマネジメント手法。過剰在庫や欠品を防ぐことが主な狙い
- **CRM（顧客関係管理）**：顧客の属性・購買履歴などの情報を一元管理し、顧客一人ひとりとの関係を強化・維持していくためのマネジメント手法・システム
- **SFA（営業支援システム）**：営業担当者の商談状況や案件の進捗などを可視化・管理し、営業活動を効率化・標準化するシステム
- **POSシステム（販売時点情報管理）**：商品が販売された時点で、いつ、何が、いくつ売れたかという情報をリアルタイムに記録・集計する仕組み。小売店のレジで広く使われている

### 具体例

コンビニのレジでバーコードを読み取ると、その商品の販売実績がPOSシステムに記録され、発注担当者はその販売データを見て翌日の発注量を決めます。この販売データが、メーカー・卸・小売の間で共有され、生産計画や配送計画にまで反映されるようになれば、それはSCMの領域に発展した活用と言えます。一方、会員カードの購買履歴を分析して、顧客ごとに異なるクーポンを配信する仕組みはCRMの活用例です。

### ひっかけポイント

SCMは「供給側（調達・生産・物流）の最適化」、CRMは「顧客側（販売後の関係維持）の管理」というように、対象とする範囲・向いている方向が異なる点を区別しましょう。「SCMとCRMは同じ概念で、呼び方が違うだけである」という理解は誤りです。また、ERPは「特定の1つの業務（例えば会計だけ）を管理するシステム」ではなく、複数の基幹業務を横断的に統合する点が特徴である点も押さえておきましょう。

## F-16：情報システム開発（ウォーターフォール型）

### 基本概念

**ウォーターフォール型開発**は、システム開発の工程を上流から下流へ、滝が流れ落ちるように一方向に順番に進めていく開発手法です。代表的な工程は次の通りです。

1. **要件定義**：利用者が何を実現したいか（システムに求める機能・要件）を明確にする
2. **外部設計（概要設計）**：利用者から見える部分（画面、帳票など）の仕様を設計する
3. **内部設計（詳細設計）**：プログラムの内部構造など、開発者側の視点での詳細な設計を行う
4. **プログラミング（コーディング）**：設計書に基づき実際にプログラムを作成する
5. **テスト**：プログラムが正しく動作するか検証する。小さい単位から大きい単位へ、**単体テスト（プログラム単位）→結合テスト（複数プログラムの連携）→システムテスト（システム全体）→運用テスト（実際の利用環境での最終確認）**の順に行う
6. **運用・保守**：本番環境で稼働させ、必要に応じて修正・改善を行う

各設計工程と、対応するテスト工程を線でつなぐと「V」の字の形になることから、この対応関係を**V字モデル**と呼びます（要件定義⇔運用テスト、外部設計⇔システムテスト、内部設計⇔結合テスト、プログラミング⇔単体テストという対応）。

ウォーターフォール型は、工程ごとに完了を確認しながら進めるため計画・管理がしやすい一方、後の工程で問題が見つかると、前の工程まで戻ってやり直す**手戻り**のコストが非常に大きいという弱点があります。そのため、開発着手前に要件を確定できる大規模・要件変更の少ない案件に向いているとされます。

### 具体例

銀行の勘定系システムのように、要件が明確で、後から仕様が大きく変わることが想定しにくく、かつ高い品質・確実な検証が求められるシステムの開発では、工程を段階的に確実に進められるウォーターフォール型が採用されやすい傾向があります。

### ひっかけポイント

「ウォーターフォール型は、要件変更に柔軟に対応しやすい開発手法である」という記述は誤りです。むしろウォーターフォール型は、前の工程に戻る手戻りのコストが大きいため、開発途中の要件変更には弱い手法です（変化への追従性が高いのはF-17で扱うアジャイル型です）。テストの順序（単体→結合→システム→運用）を入れ替えるひっかけにも注意しましょう。

## F-17：情報システム開発（アジャイル型、インクリメンタル型）

### 基本概念

**アジャイル型開発**は、要件のすべてを最初に確定させるのではなく、小さな機能単位（**イテレーション**、または**スプリント**）で「計画→設計→実装→テスト」のサイクルを繰り返しながら、少しずつシステムを完成させていく開発手法です。変化への対応力が高く、利用者のフィードバックを開発の早い段階から反映できるのが特徴です。

アジャイル型の代表的な手法が**スクラム**です。主な役割・イベントは次の通りです。

- **プロダクトオーナー**：開発する機能の優先順位を決める責任者
- **スクラムマスター**：チームがスクラムの進め方どおりに機能するよう支援する役割
- **プロダクトバックログ**：開発すべき機能の一覧（優先順位付きのToDoリスト）
- **スプリント**：1〜4週間程度の開発の反復単位
- **デイリースクラム**：開発チームが毎日短時間（15分程度）行う進捗共有ミーティング（前日の進捗・当日の予定・障害要因を共有する場であり、成果物のお披露目の場ではない）
- **スプリントレビュー**：スプリントの終わりに、完成した機能をステークホルダー（利害関係者）に見せてフィードバックを得る場
- **スプリントレトロスペクティブ（振り返り）**：スプリントの進め方自体を振り返り、次のスプリントの改善につなげる場

もう1つの代表的な手法が**XP（エクストリーム・プログラミング）**です。2人のプログラマが1台の端末を共同で使い、一方がコードを書き、もう一方がリアルタイムでレビュー・助言を行う**ペアプログラミング**、コードを書く前にテストを先に作成する**テスト駆動開発**、こまめにプログラム全体の設計を整理し直す**リファクタリング**などのプラクティス（実践方法）で知られます。

開発と運用を厳密に分離せず、両者が密接に連携して自動テスト・自動デプロイの仕組み（**CI/CD**：継続的インテグレーション／継続的デリバリー）を活用し、リリースサイクルを高速化する考え方・文化を**DevOps**と呼びます。

その他、システムの全体像をあらかじめモデル化したうえで、優先度をつけた機能単位で計画・設計・構築を反復して進める開発の進め方は**インクリメンタル型（段階的モデル）**と呼ばれます。また、GUIベースの開発ツールを使い、手書きのソースコードを最小限に抑えて開発する手法を**ローコード開発**（さらにコードをほとんど書かない場合は**ノーコード開発**）と呼びます。

### 具体例

新しいスマホアプリを開発する際、最初から全機能を作り込むのではなく、まず「ログイン機能」だけを2週間で作って利用者に試してもらい、フィードバックを踏まえて次の2週間で「投稿機能」を追加する、というように小さい単位で反復しながら開発を進めるのがアジャイル型の考え方です。

### ひっかけポイント

「デイリースクラムは、スプリントの成果をステークホルダーに提示しフィードバックを得る場である」という説明は誤りで、これはスプリントレビューの説明です。「ローコード開発とは、システムの全体像をモデル化し優先度をつけた機能単位で反復的に開発する進め方である」という説明も誤りで、これはインクリメンタル型の考え方の説明です（ローコード開発は、コードを書く量を減らす開発の"手段"を指す用語）。「DevOpsは開発と運用のフェーズを明確に分離する考え方である」という説明も誤りで、DevOpsの本質は開発と運用の密接な連携です。似た用語に正しい定義文を取り違えて当てはめるパターンの出題が非常に多いため、用語と定義を1対1で正確に結びつけて覚えることが重要です。

## F-18：組織と人材（プロジェクトマネジメント、サービスマネジメント）

### 基本概念

システム開発を計画通りに進めるための知識体系が**プロジェクトマネジメント**です。代表的な標準がPMBOK（Project Management Body of Knowledge）で、プロジェクトを「立上げ→計画→実行→監視・コントロール→終結」という5つのプロセス群で捉えます。

計画段階で重要な手法の1つが**WBS（Work Breakdown Structure、作業分解構成図）**です。プロジェクト全体の成果物を、階層的に細かい作業に分解していく手法で、次の用語が重要です。

- **ワークパッケージ**：WBSで分解した最下位レベルの作業単位。進捗・コストを管理する際の最小単位となる
- **100％ルール**：WBSの各階層において、上位の作業（成果物）の範囲を、抜け漏れなく・重複なく下位の複数の作業に分解しなければならないという原則
- **WBS辞書**：WBSの各構成要素（ワークパッケージ等）ごとに、作業内容の詳細・担当・必要資源・完了基準などを記述した補助文書（プロジェクト全体の範囲・成果物・制約条件を記述する「スコープ記述書」とは別の文書である点に注意）
- **ローリングウェーブ計画法**：早期に着手する作業は詳細に計画し、将来の作業は概略にとどめておき、時期が来たら順次詳細化していく反復的な計画技法（アジャイル開発における反復単位である「イテレーション」とは別の概念）

作業の順序関係を図示し、プロジェクト全体の所要期間を把握する手法として**PERT図**があり、そこで最も時間のかかる作業経路（この経路が遅れるとプロジェクト全体が遅れる）を**クリティカルパス**と呼びます。

システムが稼働し始めた後の運用管理の考え方を**サービスマネジメント**と呼び、代表的な指針が**ITIL**です。発生した障害に迅速に対応し、業務への影響を最小限にとどめる**インシデント管理**と、障害の根本原因を突き止め恒久的な対策を講じる**問題管理**を区別する点がよく問われます。

### 具体例

新システム開発プロジェクトのWBSで、「要件定義」という上位の作業を、「業務ヒアリング」「要件一覧の作成」「レビュー」という3つの下位作業に、抜け漏れ・重複なく分解するのが100％ルールの適用例です。また、システム障害が起きた際、まず一時的な回避策で業務を復旧させる（インシデント管理）とともに、後日、障害の根本原因を調査し再発防止策を講じる（問題管理）というように、対応の性質によって管理のフェーズを分けます。

### ひっかけポイント

「WBS辞書とは、プロジェクト全体の範囲や成果物、制約条件を記述した文書である」という説明は誤りで、これはスコープ記述書の説明です。「イテレーションとは、早期に完了すべき作業を詳細に計画し将来の作業は概略にとどめる反復計画技法である」という説明も誤りで、これはローリングウェーブ計画法の説明です（イテレーションはアジャイル開発の反復単位を指す用語）。このように、正しい定義文に別の用語名を当てはめて誤りとする出題パターンが頻出のため、用語同士を対で正確に覚えておきましょう。

## F-19：情報セキュリティの概念（機密性・完全性・可用性）

### 基本概念

情報セキュリティとは、企業が保有する情報資産を、様々な脅威から守ることです。情報セキュリティが確保すべき最も基本的な3つの要素（**CIA**）は次の通りです。

- **機密性（Confidentiality）**：許可された人だけが情報にアクセスできる状態を保つこと（例：アクセス権限の設定、パスワードによる保護）
- **完全性（Integrity）**：情報が正確であり、不正に改ざん・破壊されていない状態を保つこと（例：データの改ざん検知の仕組み）
- **可用性（Availability）**：許可された人が、必要なときに情報やシステムを使える状態を保つこと（例：システムの二重化、バックアップ）

近年は、このCIAに加えて、情報が本人によって作成・発信されたものであることを確認できる**真正性**、後になって「自分はやっていない」と否認されないように証拠を残す**否認防止**、誰が何をしたかを後から追跡できる**責任追跡性**、システムが意図した通りに動作することを保証する**信頼性**なども重要な要素として位置づけられています。

情報セキュリティ対策を考える上での基本的な発想が**リスクマネジメント**です。リスクへの対応方針には、リスクの原因となる活動自体をやめる**リスク回避**、対策を講じて発生確率や被害を小さくする**リスク低減**、保険や外部委託でリスクを他者に移す**リスク移転**、対策コストと見合わないリスクをあえてそのまま受け入れる**リスク受容**があります。

### 具体例

顧客情報を保管するデータベースに、担当者しかアクセスできないよう権限を設定するのは「機密性」の確保です。そのデータが第三者に不正に書き換えられていないことを確認する仕組みは「完全性」の確保です。そして、災害時にもシステムが止まらないようサーバを複数拠点に分散配置しておくのは「可用性」の確保に当たります。この3つのうち、どれを確保するための対策かを問う設問が頻出です。

### ひっかけポイント

ある対策が「機密性・完全性・可用性のどれに当たるか」を問う問題では、「情報が漏れないようにする」対策は機密性、「情報が正しく保たれるようにする」対策は完全性、「必要なときに使えるようにする」対策は可用性、と整理して判断しましょう。例えば、バックアップの取得は主に可用性（システムが使えなくなるリスクへの備え）に関わる対策ですが、改ざんからの復旧という意味では完全性にも関わる、というように1つの対策が複数の要素に関係することもある点に注意してください。

## F-20：情報セキュリティ管理・対策

### 基本概念

情報セキュリティ対策は、大きく「侵入・攻撃を未然に防ぐ対策」と「侵入されてしまった後の対応」に分けて考える必要があります。

- **ファイアウォール**：外部ネットワークと内部ネットワークの境界に設置し、あらかじめ決めたルールに基づいて通信を許可・遮断する仕組み
- **IDS（不正侵入検知システム）／IPS（不正侵入防止システム）**：ネットワーク上の不審な通信を検知し（IDS）、あるいは検知したうえで自動的に遮断する（IPS）仕組み
- **EPP（Endpoint Protection Platform）**：PCやサーバなどの端末（エンドポイント）へのマルウェア感染を未然に防ぐ、従来型のウイルス対策ソフトの発展形（侵入の**事前防止**が主目的）
- **EDR（Endpoint Detection and Response）**：端末に侵入・感染してしまった後の不審な挙動を検知し、調査・隔離・復旧を支援する仕組み（侵入**後の検知・対応**が主目的）
- **暗号化**：データを第三者に読み取られないよう変換する技術。送信者と受信者が同じ鍵を使う**共通鍵暗号方式**（処理は高速だが鍵の受け渡し方法に工夫が必要）と、公開する鍵と秘密にする鍵の組を使う**公開鍵暗号方式**（鍵の受け渡しは安全だが処理は低速）がある
- **電子署名**：公開鍵暗号技術を応用し、データの作成者が本人であること（真正性）とデータが改ざんされていないこと（完全性）を証明する仕組み
- **多要素認証**：パスワード（知識情報）に加えて、スマホアプリでの確認（所持情報）や指紋（生体情報）など、複数の要素を組み合わせて本人確認を行う仕組み。パスワードだけの認証より不正アクセスのリスクを大きく下げられる
- **ISMS（情報セキュリティマネジメントシステム）**：組織全体で情報セキュリティを継続的に管理・改善していく仕組み。国際規格の**ISO/IEC 27001**がその認証基準として知られる

近年特に被害が拡大している脅威が**ランサムウェア**（データを勝手に暗号化し、復旧と引き換えに金銭を要求するマルウェア）です。IPA（情報処理推進機構）の調査では、主な侵入経路としてVPN機器の脆弱性、リモートデスクトップの不正利用、不審メールとその添付ファイルが継続して挙げられています。対策として、バックアップデータを平常時はネットワークから切り離しておく（オフライン・オフサイト保管）ことや、感染に気づいた際はまず感染端末をネットワークから切り離して被害拡大を防ぐことが推奨されています。

### 具体例

ある中小企業でパソコンがランサムウェアに感染した場合、まず被害拡大を防ぐためLANケーブルを抜くなどしてそのパソコンをネットワークから切り離し、その後にシステム担当者やセキュリティベンダに報告する、という初動対応が推奨されます。日頃からバックアップ用の外付けハードディスクを、バックアップ作業のとき以外はネットワークや本体から切り離しておけば、仮に社内のパソコンが感染しても、バックアップデータまで暗号化される被害を防ぎやすくなります。

### ひっかけポイント

EPPとEDRの役割（EPP＝侵入の事前防止、EDR＝侵入後の検知・対応）を入れ替えるひっかけが頻出です。また「ランサムウェア対策として、バックアップ機器は常にネットワークに接続しておくべきである」という記述は誤りです。ネットワークに常時接続していると、ランサムウェアがバックアップ機器上のデータまで暗号化してしまう危険があるため、平常時は切り離しておくことが推奨されます。「感染に気づいたら真っ先に電源を切るべきである」という記述も、フォレンジック調査に必要な情報が失われる可能性があるため、必ずしも正しい初動対応ではありません（まずネットワークからの切り離しが優先されます）。

## F-21：情報システムの評価（品質評価、価値評価）

### 基本概念

完成した情報システムが「良いシステムかどうか」を評価する視点には、大きく品質面と経済面があります。

**品質評価**では、システムが備えるべき性質をいくつかの観点（品質特性）に分けて評価します。代表的な観点は次の通りです。

- **機能性**：利用者が必要とする機能を、正確に満たしているか
- **信頼性**：故障や障害が少なく、安定して稼働するか（F-11の信頼性設計の考え方とも関連）
- **使用性（ユーザビリティ）**：利用者にとって使いやすいか（F-7の内容とも関連）
- **効率性**：限られた資源（処理時間、メモリ等）で効率よく動作するか
- **保守性**：不具合の修正や機能追加がしやすいか
- **移植性**：異なる環境（他のOSやハードウェア）に移しても使えるか

**価値評価（経済性評価）**では、システム導入にかかった費用に対して、どれだけの効果（コスト削減、売上増加など）が得られたかを評価します。投資額に対する利益の割合を示す**ROI（投資収益率）**や、導入から廃棄までの総費用である**TCO**（F-11参照）などの指標が使われます。

### 具体例

新しい在庫管理システムを導入した際、「入力ミスが減ったか」（機能性・信頼性）、「現場の担当者が迷わず操作できるか」（使用性）、「将来の店舗拡大にも対応できる作りになっているか」（保守性・移植性）といった品質面の評価と、「システム導入費用に対して、どれだけ在庫ロスのコストを削減できたか」（ROI）という経済面の評価の両方を行うことで、システム投資が成功だったかどうかを総合的に判断できます。

### ひっかけポイント

品質評価の各観点（機能性・信頼性・使用性・効率性・保守性・移植性）は名前が似ているため、それぞれが何を指すかを混同しないようにしましょう。特に「効率性」（限られた資源での動作の良さ）と「効果性」（目的をどれだけ達成できたか、という別の観点で語られることもある概念）を取り違えないよう注意が必要です。また、品質面の評価と、費用対効果を測る経済性の評価は、異なる評価軸である点も区別しておきましょう。

## F-22：意思決定支援：問題分析・意思決定技法

### 基本概念

経営における意思決定を、勘や経験だけに頼らず、数理的な手法で支援する技法群です。

- **線形計画法（LP：リニア・プログラミング）**：複数の制約条件（原材料の量、人員の稼働時間など）のもとで、利益を最大化する、あるいはコストを最小化するような、複数製品の最適な生産量の組み合わせを求める数理的手法
- **デシジョンツリー分析（決定木分析）**：意思決定の選択肢と、その結果として起こりうる不確実な事象を、樹木のように枝分かれさせて図示し、それぞれの選択肢の期待値（見込まれる成果の平均的な大きさ）を計算して、最も有利な選択肢を選ぶ手法。図では、意思決定者が選べる分岐点を四角（□）、確率に左右される不確実な分岐点を丸（○）で表す
- **PERT図（アローダイアグラム）／CPM（クリティカルパス法）**：複数の作業の順序関係をネットワーク図で表し、プロジェクト全体の所要期間や、最も時間のかかる経路（クリティカルパス）を求める手法
- **待ち行列理論**：窓口の数やサービスにかかる時間などの条件から、行列の長さや待ち時間を予測・分析する理論（コールセンターの受付窓口の数を検討する場合などに応用される）
- **感度分析**：計画の前提となる条件（売上予測、原価など）が変化したときに、結果（利益など）がどれだけ変化するかを分析し、計画のリスクや不確実性を検討する手法

### 具体例

ある町工場が2種類の製品を作っているとします。それぞれの製品に必要な原材料の量と、工場の1日あたりの原材料の在庫量（制約条件）が決まっている中で、利益を最大にするにはそれぞれ何個ずつ作れば良いかを求めるのが線形計画法の典型的な使い方です。また、新製品を開発するかどうかを判断する際、「市場が好調な場合の利益」「不調な場合の損失」とそれぞれの発生確率を樹木状に整理し、期待値を計算して意思決定するのがデシジョンツリー分析の使い方です。

### ひっかけポイント

デシジョンツリーの図で、意思決定者自身がコントロールできる分岐点（四角：□）と、確率に左右されコントロールできない分岐点（丸：○）を取り違えないようにしましょう。また、線形計画法は「利益の最大化」だけでなく「コストの最小化」を目的とする場合もあるため、「必ず利益の最大化を目的とする手法である」と限定して覚えないよう注意してください。

## F-23：意思決定支援：データ分析技術と活用

### 基本概念

蓄積されたデータから、経営上有益な情報やパターンを見つけ出す技術です。

基本的な統計指標として、データの中心的な傾向を示す**平均**、データのばらつきの大きさを示す**分散**・**標準偏差**、2つの変数の間にどれだけ直線的な関係があるかを示す**相関係数**（-1から1の値をとり、0に近いほど関係が弱く、絶対値が1に近いほど強い直線的な関係がある）があります。

- **回帰分析**：ある変数（説明変数）から、別の変数（目的変数）の値を予測する式を統計的に求める手法。説明変数が2つ以上ある場合は特に**重回帰分析**と呼ぶ
- **多変量解析**：多数の変数を同時に扱い、データの背後にある構造やパターンを分析する手法群の総称。次のような手法が含まれる
  - **主成分分析**：多数の変数が持つ情報を、できるだけ情報量を保ったまま少数の合成変数（主成分）に要約する手法
  - **因子分析**：観測されたいくつもの変数の背後に共通して存在する、直接は観測できない要因（因子）を推定する手法
  - **クラスター分析**：性質の似ているもの同士をグループ（クラスター）に分類する手法
  - **判別分析**：あらかじめ決められたグループのどれに当てはまるかを判別するためのルールを、データから作り出す手法
- **BIツール（Business Intelligence ツール）**：蓄積された社内データを可視化・集計・分析し、経営判断を支援するソフトウェア

### 具体例

ある小売チェーンが、来店客数と気温のデータから「気温が1度上がると来店客数が何人増えるか」という関係式を求めるのは回帰分析です。また、多数の顧客の購買データをもとに「よくまとめ買いする客」「単価の高い商品を好む客」のようにいくつかのグループに分類するのはクラスター分析の活用例です。BIツールを使えば、こうした分析結果をグラフやダッシュボードの形で経営者に分かりやすく提示できます。

### ひっかけポイント

「2つの変数に相関関係が見られれば、必ず一方がもう一方の原因である（因果関係がある）と言える」という考え方は誤りです。相関関係はあくまで「一緒に動く傾向がある」ことを示すに過ぎず、因果関係の証明にはなりません（見せかけの相関の可能性もあります）。また、主成分分析（変数を要約すること自体が目的）と因子分析（背後の共通因子を推定することが目的）は似た多変量解析の手法ですが、目的が異なる点を区別しておきましょう。

## F-24：意思決定支援：データサイエンス（AI、確率・統計）

### 基本概念

近年、経営情報システムの科目でも出題が急増している分野が、AI（人工知能）とデータサイエンスです。

**機械学習**とは、コンピュータが大量のデータからパターンやルールを自動的に学習する技術で、大きく3つに分類されます。

- **教師あり学習**：あらかじめ「正解」が付いたデータ（例：過去の顧客データと、実際に商品を購入したかどうかの結果）を使って学習し、新しいデータに対する予測（分類・回帰）を行う
- **教師なし学習**：正解データを与えず、データそのものが持つパターンや構造（グループ分けなど）を発見する（F-23のクラスター分析なども教師なし学習の一種として扱われることがある）
- **強化学習**：試行錯誤を繰り返しながら、得られる報酬（成果）が最大になるような行動のルールを学習していく

**ディープラーニング（深層学習）**は、人間の脳の神経回路を模した「ニューラルネットワーク」を多層に重ねた構造を用いる機械学習の一手法で、画像認識や音声認識、生成AIなど幅広い分野で高い性能を発揮しています。

近年急速に普及した**生成AI**に関連する重要用語も押さえておきましょう。

- **LLM（大規模言語モデル）**：大量の文章データを学習し、人間の自然な文章に近い形で文章の生成・要約・翻訳などを行うAIモデル（ChatGPT等の基盤技術）
- **ハルシネーション**：AIが、事実に基づかない、もっともらしい誤った情報をあたかも真実であるかのように生成してしまう現象。生成AIを業務で利用する際の重要なリスクとして注目されている

意思決定支援の土台となる確率・統計の基礎知識として、ある事象が起きた「条件のもとで」別の事象が起きる確率を表す**条件付き確率**や、新しい情報が得られるたびに、事前の確率（見込み）を更新していく考え方である**ベイズの定理**も出題対象です。

### 具体例

過去の融資先データ（正解：返済できたか、延滞したか）を使って、新規の融資申込者が延滞するリスクを予測するモデルを作るのは教師あり学習の応用例です。一方、購買履歴データだけから「似た買い方をする顧客グループ」を自動的に発見するのは教師なし学習の応用例です。また、生成AIチャットボットに自社の製品について質問したところ、実際には存在しない機能をもっともらしく回答してきた、というのはハルシネーションの典型的な例であり、生成AIの回答をそのまま鵜呑みにせず事実確認する必要性を示しています。

### ひっかけポイント

「教師あり学習とは、正解データを使わずにデータのパターンを発見する手法である」という説明は誤りです（それは教師なし学習の説明）。教師あり学習と教師なし学習は、「正解データの有無」で区別される点を正確に覚えましょう。また、「ハルシネーションとは、AIが個人情報を漏洩させてしまう現象である」という説明も誤りです。ハルシネーションはAIが事実に基づかない誤った内容を生成してしまう現象を指し、情報漏洩とは別の問題です。
